## 已落地的能力

学习者提出课程问题，再追问变体、后续步骤或停止条件。模型选择搜索、授权片段补读或独立解释；原文观察和复核拒绝影响下一次修订。解释、引用、Run、工具结果和逐项复核保存在原 Python/PostgreSQL 链路。

- `course_relations_v2` 要求每个被审核断言返回当前答案片段、来源关系类型、授权 Evidence 原文片段和支持判定。片段必须逐字属于当前断言及其自身可见来源；支持判定不能同时报告缺口。片段成员校验不证明语义蕴含，缺口分类不是可信纠错结论。
- 修订反馈只传递有界的被拒断言和原文观察，不把模型分类转换为答案。最终修订保留完整目标检查、Unicode 位置和全部断言覆盖。
- `atomic_ledger_v7` 和差异复核重新校验原文绑定、策略、owner/course/revision/session 及来源内容。旧策略记录保持可读，不直接提升为新策略已验证事实。
- 每次来源复核使用 1,600 输出 token 上限，并纳入实际请求计价与持久预留。首轮修订也使用已有的无损 schema 精简；不删除校验约束。Run 仍最多 6 次模型、8 次工具、64,000 保守预留、90 秒及两份候选。
- 工具格式重试把纠错观察放入原结构化决策上下文，修复追问重试中的 `JSONDecodeError`。原预算不足仍明确停止，不增加隐式重试。
- 浏览器入口改为“开始学习”，补齐解释产物类型、解释完成状态与工具名称；没有练习时隐藏作答/答案控件。新增 [浏览器检查脚本](check_browser.py)。

取消、授权或版本变化、删除、协议失败、预算和时间耗尽、两份候选未通过均停止。Java/MySQL 的权威边界没有在本阶段扩展；事实账本不是长期学习记忆。

## 开发证据与失败

关系原型的 30/30 二元诊断没有在运行时自动重现。早期集成候选的固定开发诊断为 29/30，另一个提示版本虽也为 29/30，却重新放过无依据排序指标，因此淘汰。精简提示后诊断进一步降至 25/30，也已淘汰；最终恢复较完整的来源复核提示，保留无损传输与协议恢复修复。

真实测试继续使用预先记录的三组三轮背包对话，以及历史递归追问。每次开始前另存候选身份，失败后停止该组后续依赖轮次，其余独立组继续。部分 Run 执行成功，但解释将课程的黄金、白银、葡萄干顺序解释为“单位价值排序”，严格来源核查判失败，原产物和账本保留供审计。另有预算无法准入、最终复核协议失败、修订耗尽，以及已修复的格式重试内部错误。

三次候选切换后的评测初始化请求在服务尚未就绪时返回 503，尚未发出 START；这些基础设施失败另列，不冒充模型任务试次。后续队列等待隔离 Agent 的 healthz 就绪，使用新输出目录，没有覆盖旧记录。

失败记录说明：绑定原文能验证来源身份，仍不能保证模型正确识别遗漏条件、关系方向或无据属性；固定草稿诊断也不能代表完整生成和多轮修订。未执行的后续目标不是通过，Run succeeded 不等于语义正确。本阶段使用 AI 来源核查，没有独立盲审人工金标。
