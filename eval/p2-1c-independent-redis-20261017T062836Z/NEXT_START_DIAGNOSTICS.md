# 后续受控启动诊断的最小方案（本轮未运行）

本轮 Redis 隔离、最终配置门禁和原 bootstrap 指纹均通过。随后完整 Java 以 1 退出，未到 readiness、未提交课程任务。

当前日志投影只记录门禁/处理阶段，未保留框架初始化异常。原 logback 使用控制台及 %nopex，没有本轮文件 appender；Java 原始输出仅在内存中经过过滤，不保存未匹配行，已经无法事后恢复异常。不得猜测是数据库、MQ、权限或类路径问题。

已准备 `P21StartupDiagnostics.java` 作为下次额外 instrumentation，**本轮仅离线自测，未用于真实启动**：调用原 P21Bootstrap；异常时最多输出 16 层固定类别，以及 SQLException 的格式受限 SQLState / 整数 vendorCode；不输出异常消息、堆栈、bean 名、路径、URL、配置、密钥或响应。自测覆盖类别、消息排除、环路有界及非法 SQLState 排除。

后续启动适配器需在独立副本中仅替换 instrumentation 主类为该 wrapper，并让 stdout 投影只接受固定类别枚举及受限 SQL 字段。原 bootstrap 源码、版本 10/指纹校验、最终隔离门禁、冻结 JAR、cache OFF、C/E 关闭和全部预算继续保留。不得用该 wrapper 覆盖冻结类。

下一步建议先做**仅启动诊断、不提交任务**：新建同范围独立临时 Redis，经过原预检、启动到 readiness 或异常后安全停止；禁止在该诊断入口调用 trial。原因确认并解决后，再依据原冒烟与正式十次门禁推进。

所需授权仅为：再次创建同范围的独立临时 Redis，以及指定 dev 临时 unit 的一次受控启动诊断并最终清理。用户既有“重启前先停下”边界适用；本轮没有再次启动。无需新增凭据来源、修改模型绑定、放宽指纹或供应商调用预算。任何新权限需求、隔离不成立或磁盘门禁失败仍停止。
