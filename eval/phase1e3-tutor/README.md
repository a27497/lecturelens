Run `preflight.py` with the locked Agent Python interpreter and a fresh `--instance phase1e3-*`. Supply `--output-dir`, the verified private `--archive`, `--upstream-dir` with the pinned lesson downloads, and a cached local `--embedding-cache-source`. The default path stages four separate course tasks in an isolated Java/MySQL/PG stack, checks all ten frozen retrieval positions and executes one clearly labelled Mock HTTP wire round trip. It only creates an `offline-fake` receipt.

The live path additionally requires `--live --confirmed-price-id deepseek-flash-peak-usd-2026-11-09`, a clean committed checkout, and explicit key injection. Before launching, reconfirm the published model and peak pricing. Inject `TUTOR_FLASH_API_KEY` into the dedicated command environment with your secret manager or a hidden terminal prompt and set `LECTURELENS_E3_KEY_INJECTED=phase1e3` for that command. Keep the key out of command arguments, shell history, files and logs. The ordinary process supervisor strips provider environment variables. Use it for offline checks and use a dedicated controlled terminal for the separately authorized live launch. [DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing/)

The runner preflights before claiming the one live phase anchor in `.data/phase1e3/`. It retains the live PostgreSQL and MySQL volumes, anchor, dispatch markers and private audit output. A known in-flight request has a durable reservation and dispatch marker before HTTP. A restored or incomplete ledger that disagrees with the dispatch markers cannot spend. Preserve the marker directory outside database snapshots. The runner records exact request and bounded response entity bodies, status and completeness, with no authorization headers. Pending or interrupted transport stays an outstanding liability.

The runner submits frozen positions in order, exports a blind review packet for each actual eligible reply, and requires two independent pass decisions before advancing. Supply `--review-wait` for a bounded wait per reply. The default ends the run at the first unresolved review. Leave remaining positions unobserved after a stop. In the resulting directory, `result.json` contains the outcome, `journal.json` the turn checkpoints, `ledger.json` the run receipts, and `wire/` the request/response bytes. The reports are private and gitignored.

## One possible development retest

A retest needs an observed, repairable **development** failure, a recorded root-cause/repair evidence SHA, one bounded fix and a new committed build with passing offline checks. A holdout result cannot authorize a retest or prompt change. Use `approve_retest` with the original receipt, the observed development case and the repair evidence digest. This closes the initial dispatch path. Provision the distinct `retest` target in the **same** database. Issue one short-lived retest receipt for an ordered subset of the original development dialogue prefixes with the same course, version and evidence bindings. Use the same live anchor and dispatch-marker directory. Launch the isolated E3 worker with the new commit/receipt, the same preserved database and a fresh secure injection, and submit only those positions through Java. The phase request count and settled plus outstanding liability are read under the same PostgreSQL lock before either run reserves.

The phase permits at most 10 initial requests and 6 development retest requests, with a USD 10 cumulative gate and the existing narrower per-run budget.
