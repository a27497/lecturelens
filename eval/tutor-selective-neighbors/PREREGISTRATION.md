# LL-P15 retrieval preregistration

Baseline is main at `ef6fcd2b9fc566df92cb7f98fc98de561e911737` (PR #86). The comparison unit is one unique frozen L4 development question on its original course, owner and Evidence revision, with empty dialogue. Each arm runs once on all 30 questions. All arms use the exact #86 ordered query strings, including the existing comparison and multipart splits. Runtime strategy dispatch uses the number of targeted queries before any existing dialogue hint is appended.

| Arm | One targeted query | Multiple targeted queries |
| --- | --- | --- |
| Main (#86) | Hybrid Top 8 | Hybrid Top 16 per query |
| All queries + neighbors | Hybrid Top 8 + neighbors | Hybrid Top 8 + neighbors per query |
| Selective (product) | Hybrid Top 8 + neighbors | Hybrid Top 16 per query |

The historical L4 dev table used “Hybrid 8 + neighbors” for a single-query ablation with splitting disabled. Its “Routed hybrid 8 + neighbors” arm used plain Hybrid 8 on simple questions. Here the all-queries arm retains #86 splitting and applies expansion to each query, so the comparison isolates evidence selection.

The signed Java path selects only authorized retrievable excerpts and checks course version before and after each operation. Dense ranking uses the frozen MiniLM index and best cosine score per Evidence ID, with ID tie-breaks. Java requests up to two eight-result pages, excluding the IDs from page one. BM25 uses the existing Java tokenization and constants (k1 1.2 and b 0.75), with the ID breaking score ties. Within each ranked list, a translated subtitle maps to the first original with the same interval when present, and duplicate excerpts retain their first position. Java fuses the dense and top 16 positive lexical candidates by reciprocal rank with k=60 and ID breaking ties. It then keeps the ordered 8 or 16 anchors.

Where enabled, the existing neighbor strategy keeps all anchors first. In anchor-rank order it tries each anchor's immediate successor, then in a second pass its predecessor, within the same source type. Each source timeline sorts by start time, end time and Evidence ID. It keeps the first occurrence and stops at 16 per query. Python deduplicates each query by Evidence ID, applies reciprocal rank fusion across the existing queries (k=60, ties by first query index, rank and Evidence ID), and keeps at most 16 distinct IDs. Authoritative READ uses batches of at most eight, verifies all expected IDs and nonempty text, and restores fused order. Coverage and bytes use the resulting `current_evidence`.

A vital nugget is covered when at least one sufficient Evidence group from the original support mapping is wholly present. Full required coverage is the number of answerable questions with every vital nugget covered divided by the number of answerable questions. Vital coverage sums covered vital nuggets over all vital nuggets. Cross-segment full coverage is the same full-question measure restricted to the frozen cross-segment category.
